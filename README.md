# AI Radar

> 每天自动扫一遍信息源，按「对我有没有用」打分，只把 ≥7 分的推给我。

一个跑在自己机器上的个人信息雷达：抓取 → 去重 → LLM 结构化打分 → 生成日报 → 邮件推送。
目标是把「每天花 40 分钟刷信息」压到「3 分钟看完一份摘要」。

**当前状态**：第 N 天运行中 · 累计处理 M 条 · 日均成本 ¥X.XX
（诚实填写，跑几天写几天。真实比漂亮重要。）

---

## 它解决什么问题

RSS 阅读器只做「聚合」，不做「筛选」。订阅 20 个源之后，每天仍然是 100+ 条未读，最后干脆不看。

这个工具做的是**按人筛选**：给定一份用户画像（我在学什么、我要找什么），让模型判断每条内容值不值得我看，并说明理由。低分的直接埋在「略过」里，不占注意力。

- 和 RSS 阅读器的区别：它替你做判断，而不是把判断留给你
- 和「订阅号助手」的区别：打分标准是我自己的画像，不是编辑的口味
- 和「让 AI 每天给我总结新闻」的区别：有状态、有去重、有成本控制、能长期跑

## 架构

```
 .env (画像/信息源/密钥)
        │
        ▼
 ┌─────────────┐   ┌──────────────┐   ┌───────────────┐   ┌────────────┐
 │  Fetch      │──▶│  Dedupe      │──▶│  Analyze      │──▶│  Render    │
 │  RSS / Atom │   │  sha1(hash)  │   │  LLM + JSON   │   │  Markdown  │
 │  重试 2 次   │   │  SQLite 状态  │   │  字段校验+兜底 │   │  + Email   │
 └─────────────┘   └──────────────┘   └───────────────┘   └────────────┘
        │                  │                   │                  │
        └──────────────────┴───────────────────┴──────────────────┘
                                   │
                            runs 表：抓取数/新增/失败/tokens
                            （心跳与成本都从这里看）
```

## 关键设计取舍

**1. 去重靠「归一化 URL 的 hash」，不靠标题**
同一篇文章换个标题转载很常见。URL 去掉 `?utm_*` 和各查询参数后再 hash，能覆盖 90% 的重复。

**2. 结构化输出 + 自己再校验一遍**
模型输出 JSON（relevance/summary/reason/tags/action），但代码不信任它：分数裁剪到 0–10，字段截断，`tags` 可能是字符串也可能是数组。**LLM 的输出要当成不可信输入处理**——这一点和防止提示注入是同一个原则。

**3. 单条失败不拖垮整批，但整体失败要能被发现**
每个源、每条内容都有独立的 try/except。失败率过半时返回非零退出码，让 Windows 任务计划程序 / cron 能据此告警。**静默失败比报错更危险。**

**4. 先不引入任何第三方依赖**
只用标准库（urllib / sqlite3 / xml.etree）。为的是「换台电脑 30 秒能跑起来」。等真正需要了再引入 feedparser、httpx、pydantic。

**5. 两维打分，加权由代码算**
让模型分别判断「相关度」和「可行动性」这两个正交的维度，加权分（0.6×相关 + 0.4×可用）在代码里算。
原因：模型做算术经常错，而且判断标准应该能在代码里调，不该写死在 prompt 里。
副产品：每条内容都能解释「为什么是这个分」——相关 8 分但可用 2 分，和反过来，是两个完全不同的信号。

**6. 原始正文入库**
一开始只存标题和链接，改一次 prompt 就得重新抓一遍，而且抓不到已经过期的内容。
现在正文落库，`--reanalyze` 可以离线重打分。**判断标准一定会变，所以原始数据必须留。**

**7. 换过一轮信息源**
v0.1 用的是 Hacker News 首页 + 科技周刊 + 消费数码媒体，22 条里只有 1 条 ≥7 分。
不是模型不行，是它看的世界不对：HN 首页讲的是「科技圈今天聊什么」，不是「AI 工程」。
换成 Simon Willison / HN 的 LLM 关键词流 / Latent Space / GitHub Trending / InfoQ 之后，命中率显著上升。
**信息系统的质量 = 输入质量 × 判断标准 × 处理流程，输入是 0，后面两项再完美也是 0。**

**8. 名额制，不是阈值制**
换源之后出现新问题：77 条里 25 条 ≥7 分——25 条「必看」等于没有必看。
根因是绝对阈值在源数量变化时会漂移。改成：先按分数排序，再按名额截断（必看 5 / 值得看 10 / 速览 10）。
阈值回答「这条好不好」，名额回答「今天最该看哪几条」。日报要的是后者。

**9. 日报从「今日全库」重建，而不是只用本次新增**
一天跑两次不会互相覆盖；改了版式可以 `--render` 重出，不抓取、不调用模型、不花钱。
代价是需要把正文留在库里——这也是第 6 条的理由。

## 快速开始

```bash
git clone <your-repo>
cd ai-radar
cp .env.example .env          # 然后填 LLM_API_KEY
python radar.py --check       # 验证 API 能通
python radar.py --fetch-only  # 只看抓取，不花钱
python radar.py               # 完整跑一次
```

Windows 定时（每天 08:00）：

```powershell
schtasks /create /tn "AI Radar" /tr "python C:\path\to\ai-radar\radar.py" /sc daily /st 08:00
```

## 已知问题

- RSS 1.0（RDF 格式）未支持，遇到会直接失败
- 正文只取 `description`/`summary`，很多源只给摘要，打分信息量不足
- 没有并发，源多了会慢
- 邮件只支持发给自己
